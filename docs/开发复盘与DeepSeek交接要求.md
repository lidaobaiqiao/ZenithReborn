# 天顶复苏：开发复盘与后续交接要求

> 历史复盘：本文记录0.2.4时期。当前接手请先读[0.3.8开发交接](DeepSeek开发交接-v0.3.8.md)，不要据此回退版本或把历史验证数量当作当前状态。

日期：2026-10-18。基线：已安装的 ZenithReborn 0.2.4。

这份复盘面向继续开发本项目的模型。依据是用户提供的前次开发记录、当前源码、构建和安装记录，以及本次特效迭代中的实际反馈。对具体开发行为负责，不凭一次会话推断整个模型的能力。

本次有两个同样重要的教训：前次开发在轨迹解释、测试竞态和反复试改上消耗了过多时间；本次我也擅自增加了用户不喜欢的光效，并犯过贴图缩放错误。这些都应进入后续约束。

**1. 把用户的体验目标翻译成可以观察的行为。**

用户希望“成长性天顶剑”，已经给出了明确结构：残魂依附实体武器、逐步开放槽位、Boss诅咒逐步转为祝福、最终复生。第一阶段进一步限定为“友好史莱姆王授予附着”。这足以开始实现。

任务有一定工程量，但用户不需要先替开发者解释弹幕生命周期、贴图原点或坐标变换。接手者应主动完成技术翻译，把确实影响玩法的分歧提出来，其余常规实现自行推进。

第一阶段的可观察终点是：新残魂不能有效攻击；可以预览和取回武器；玩家获得友好史莱姆王的祝福；一个寄宿槽稳定可用；随后能够御剑。不要把第一阶段继续扩写成全流程十几个Boss的大工程。

**2. 有明确参考行为时，先研究对应对象。**

前次记录中，剑影朝向曾在瞄准方向、运动切线、外法线、固定角度和多段椭圆之间反复切换。每种数学解释都能写出代码，但不一定对应用户看到的天顶剑。

当前已经采用原版天顶弹幕933风格的实现，0.1.13的运动与朝向作为后续基线。研究手持普通剑的 Player.itemRotation，不能直接证明飞行剑影应当怎样旋转。

后续处理类似问题，先定位参考物品实际生成的弹幕、AI参数、位置公式、朝向公式与贴图基准，再修改本项目。既然已有实现可比对，就不应让用户连续体验几套猜出来的运动模型。

**3. 分开管理运动、朝向、判定和外观。**

当前职责：

| 文件 | 主要职责 |
|---|---|
| `SoulBlade.cs` | 剑影位置、朝向、命中、材料剑特殊弹幕及客户端历史采样 |
| `SoulRibbonMesh.cs` | 历史采样转为拖尾顶点与颜色，不读取游戏全局状态 |
| `SoulVisuals.cs` | 渲染拖尾网格、设置和恢复绘图状态 |
| `WeaponFamilies.cs` | 早期武器类别和可复用特性 |
| `AttachmentStory.cs` | 友好史莱姆王相遇、对话与授福 |
| `SoulItem.cs` | 寄宿武器、成长数据、物品保存与使用 |

用户要求调整特效时，运动与命中已经稳定，应保持原样。新增拖尾只读取历史位置与朝向，不能顺手改变攻击频率、轨迹、判定范围或伤害。

**4. 特效首先需要形状正确，数量应服从用户审美。**

本次实际经历：

| 版本 | 做了什么 | 得到的教训 |
|---|---|---|
| 0.2.1 | 加入光带、残影、出剑光环、收剑粒子与命中闪光、扩散圈 | 我增加了过多未经确认的视觉元素，用户明确认为太暴躁 |
| 0.2.2 | 删除光环、爆散与闪光，保留细轨迹、两道淡残影与少量粒子 | 克制的方向正确，但保留下来的轨迹绘制仍存在贴图缩放错误 |
| 0.2.3 | 校正MagicPixel绘制尺寸与旋转中心 | 修复截图中跨越大半屏幕的巨大色带 |
| 0.2.4 | 根据用户参考图实现剑身扫出的弧面渐变拖尾 | 参考图使目标变得具体，用户对结果给出“完美”的反馈 |

“特效单调”不能自动扩展成光环、闪屏、爆炸和大量粒子。收到参考图后，应提取几个真正决定观感的要素：弧面宽度、亮边位置、横向透明过渡、尾端收细与淡出、武器本体是否清楚。

**5. 单位与API语义错误，不能靠调整参数掩盖。**

巨大色带的原因是绘制完整贴图时，把目标像素长度直接作为Sprite缩放倍率。Sprite绘制的关系是：

```text
绘制宽度 = 源矩形宽度 × 横向缩放
绘制高度 = 源矩形高度 × 纵向缩放
```

源矩形为null时，使用整张贴图的宽高。不能假设名叫MagicPixel的贴图一定只有1×1像素。

当时的正确修复是：

```csharp
scaleX = desiredLength / texture.Width;
scaleY = desiredWidth / texture.Height;
origin = new Vector2(0, texture.Height * 0.5f);
```

这里还要同时核对旋转中心。只调透明度或把宽度从4改成1，会隐藏症状，却保留错误的尺寸关系。

**6. 线状轨迹和剑身扫出的弧面，需要不同的几何表达。**

用户最后提供的参考图需要沿剑身扫出的带状曲面。当前0.2.4的实现为：

- 最多保留24个位置与朝向样本，实际长度随单次飞行时长调整。
- 相邻样本使用Catmull-Rom曲线细分，朝向差经过WrapAngle处理。
- 根据物品贴图对角线与缩放估算剑身长度，限制尺寸上界。
- 横截面设置内侧透明、中部柔和、剑尖亮边、外缘透明四排顶点，连接成三个带状区域。
- 尾部宽度与透明度分别衰减，避免整条拖尾同样宽、同样亮。
- 使用BasicEffect与顶点颜色、AlphaBlend绘制，复用顶点缓冲数组。
- 在PostDrawTiles阶段绘制拖尾，后续绘制武器主体；不打断剑影的SpriteBatch。
- GPU资源在绘制线程创建并安排释放，专用服务器跳过图形处理，绘制结束恢复相关状态。
- 位移断点超过300像素时拒绝连接，避免瞬移形成横贯屏幕的拖尾。

当前上限为1656个顶点，即552个三角形/条；这是几何复杂度上限，不是实际帧率测试结果。

**7. 测试必须覆盖故障发生的路径。**

前次UI检查曾反复失败：加载线程模拟鼠标和缩放时，主线程还在改写相同的全局状态。正确动作是修复测试的线程与坐标前提，并在主线程执行相关交互检查。反复重跑直到偶然通过，不能证明竞态消失。

重铸丢武器也说明了路径差异：哥布林重铸与HERO前缀编辑器不是同一个入口。HERO可能重建物品对象，绕过常规重铸钩子。必须沿实际丢失数据的入口检查，保护寄宿物品、前缀、SoulId、Boss铭刻、魂芯和祝福字段。

记录结果时区分证据：

| 证据 | 能证明的内容 |
|---|---|
| 编译通过 | 代码满足编译与引用要求 |
| 无窗口加载和功能检查 | 实际加载与指定逻辑路径可执行 |
| 网格边界、透明度、镜头平移检查 | 几何与颜色数据满足指定约束 |
| 实际顶点数据的离线预览 | 指定样本的形状与渐变可观察 |
| 图形客户端实测 | 被实际操作过的游戏行为与画面 |
| 真实多人测试 | 被覆盖的联机交互和同步行为 |

这些证据不能相互替代。0.2.2通过26项功能检查后，画面仍能出现巨大色带，就是直接的反例。当前35项检查包含9项拖尾几何检查，也不能被写成“完整实战和多人全部通过”。

**8. 保护玩家已经投入的进度。**

新增祝福、成长或寄宿规则时，先明确旧档如何迁移。当前旧剑魂已有寄宿武器或成长数据时保留可用状态；保存、克隆、网络序列化与重铸需要覆盖新增字段。

友好史莱姆王授福也应使用自己的剧情状态，避免伪造原版Boss击杀旗标、额外发放战利品或无故开放后续槽位。

图形实验使用隔离人物与世界。正常安装只替换目标模组，备份旧包，核对实际安装路径、启用列表与成品哈希。文件被游戏占用时，请用户保存退出，等待后完成安装。

**9. 交付要完整，检查要适量。**

一次小修改通常按“完成修改→编译→针对受影响路径检查→打包→备份并安装→说明结果与未测范围”推进。遇到新失败再扩大诊断，不必为了数字好看重复跑与改动无关的全部检查。

发现需要用户退出游戏等外部条件时，先完成不依赖它的修改、检查与打包。用户配合后继续完成替换，不把已授权的剩余步骤留成一句“要不要我继续”。

本次成品：`artifacts/ZenithReborn.tmod`，版本0.2.4。安装记录：`artifacts/install-result.json`。网格预览：`artifacts/soul-ribbon-preview.png`。当前记录为35项检查通过，图形实战和真实多人并未由本次自动化完成。
