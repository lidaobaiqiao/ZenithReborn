# 项目规则：先查地图，再读源码（地图闸门）

`alwaysApply: true`。本文件与 `AGENTS.md` 的「代码库地图」章节配套，是**定位类工作的强制入口**；两者冲突时以本文件为准（更严）。
新增本文件后需**重启会话**才生效（rules/ 目录变更不会热加载）。

## 1. 触发条件（满足任一条，必须先查地图再动手）

- 要改 / 新增生产代码（`ZenithReborn/**/*.cs`）
- 要排查现象：不生效、数值不对、回归失败、崩溃
- 要回答「改这里会影响什么」「这个功能在哪个文件 / 属于哪个模块」
- 要派单给子代理做多文件改动（派单里必须写清模块归属与影响面）

**例外（可直接动手，不必查地图）**：纯文档、纯注释、同一文件内的错别字与格式、已确认文件内的单行逻辑修正。

## 2. 查的顺序（照做，不跳步）

1. `python checks/map_query.py <关键词>` —— 一步得到「模块 / 文件 / 职责 / 关联」。**这条命令就是用来替代全库 grep 的**，先跑它。
2. `docs/CODEBASE_MAP.md` 对应模块章节 —— 看依赖方向与职责边界，判断改动波及面。
3. 有具体现象 → `docs/PROBLEM_INDEX.md`；已知要改哪 → `docs/HOTSPOTS.md` 取入口与行号。
4. **最后才读源码**，并用源码确认地图是否仍然准确。

## 3. 地图与代码冲突

以源码为准，并在**同一个提交里**顺手修正地图；修正后重跑索引与校验。

## 4. 地图必须跟着代码走（实时性）

- 新增 / 删除 / 重命名文件、模块职责变化、核心入口变化、跨模块依赖变化 → 同一提交内更新 `docs/CODEBASE_MAP.md`、`docs/HOTSPOTS.md`，并重跑 `python checks/build_file_index.py` 重生成 `docs/FILE_INDEX.md`（**该文件是生成物，不许手改**）。
- 提交前跑 `python checks/map_freshness.py`：校验索引是否最新、`文件:行号` 是否失效、版本号与源码计数是否一致。该检查已挂 pre-commit 钩子，失败会拦住提交（确需绕过的用 `git commit --no-verify`，并在提交说明里写原因）。
- 计数类事实（源码文件数、回归项数、版本号）一律以脚本输出为准，不凭记忆写。改动计数后同步 `CODEBUDDY.md` 里对应的数字。

## 5. 报告要求

定位类工作的回复必须写清：**命中的模块 → 涉及文件 → 是否与源码核对过**。没查地图就不要声称「已定位」；跳过地图直接全库搜索时，如果因此漏掉跨模块影响，视为本次工作不合格。
