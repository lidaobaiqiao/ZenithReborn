# 项目开发与多代理调度政策（V3）

本文件是 ZenithReborn 项目的常驻项目规则（`alwaysApply: true`），每次会话自动加载。
编排方式以用户级单一真源 `~/.workbuddy/skills/agent-orchestration/SKILL.md` 为准（`Skill(agent-orchestration)` 直接加载）；项目内 `.codebuddy/skills/agent-orchestration/SKILL.md` 仅为入库指针。本文件只保留不冲突的项目硬规则。
版本：2026-11-04 V3（按用户下发的智能编排 Skill 协调；V2 的强制委派闸门已撤销）

## 原则
1. 按可独立验证的最小交付物拆解任务，不按通用角色或大子系统分块。
2. 用四类依赖建图，就绪即派、完成即解锁，不用批次屏障。
3. 非重叠写集合是默认隔离（本机无原生 worktree 参数）。
4. 琐碎改动直接做；代理数量不是合规指标。

委派是手段不是指标；琐碎改动直接做；按可独立验证交付物拆解；禁止以代理数量或形式派单证明合规。

## 1. 适用范围与上下文隔离（硬规则）
适用于所有开发请求、后续开发与每一个实质新阶段，直到本项目生命周期结束。排除：闲聊、问候、与执行无关的简单概念问答。
主上下文保持战略聚焦，只保留：整体架构、当前目标、任务依赖、重要技术决策、已验证结论、集成状态、未解阻塞；子代理负责原始源码检查、详细调查、试错调试、大日志、中间实现细节、常规验证。非必要不把完整调查记录、原始日志、反复失败的尝试搬进主上下文。

回交口径以 `.codebuddy/skills/agent-orchestration/delegation-contract.md` 为准。

**回交固定五项**（简洁且有证据，不接受无证据的"已完成"）：

1. Task / Status
2. Files / Changes
3. Verification / Evidence
4. Blockers / New deps（含新发现的依赖）
5. Integration notes

## 2. 派单契约与文件所有权（硬规则）
派单唯一口径 = 用户级 `agent-orchestration` 主文件 §派单模板（细则见 `delegation-contract.md`）。模板已覆盖：目标、范围与输入假设、技术约束与允许操作、`owns`/`forbid`、验证条件、交付物、超时上报、回交五项。本节不另设第二套清单。

并发纪律：
- 禁止两个代理同时改同一文件（同文件任务串行，或合并给一个所有者）。
- 并行修改共享接口前先协调，先定接口再开工。
- 有隔离工作区 / 分支 / worktree 时视情况使用。
- 遵守依赖顺序，前置未完成不启动后继。
- 并行不得损害仓库完整性；集成要显式做，不能靠运气。

## 3. 工程质量与真验证（硬规则）
- 尊重真实版本与依赖：核对 .NET 8 / C# 12 / tModLoader 1.4.4 的实际 API。
- 验证不熟悉的 API：查权威文档或源码定义后再用；**禁止编造方法、类、接口**。
- 优先根因修复，不做猜测性补丁；保留既有架构与模块拆分，避免无关改动。
- 尽可能跑真实验证（真编译、真夹具、真运行），不用推演代替；如实报告失败，不粉饰、不省略。
- 主代理对集成后的正确性负责，子代理自称成功不能替代验证。

## 4. 集成、验证与证据分级（硬规则）
宣布完成前：收齐结果 → 核对文件改动与归属 → 解决冲突 → 确认共享接口 → 跑相关构建与测试 → 独立复核关键改动 → 确认符合用户要求。
严格区分四种状态，不得混用：已实现 / 已编译 / 已通过测试 / 已实测验证；未测试的代码不得称为已验证。
证据分级固定为：**隔离夹具 ≪ 图形客户端 ≪ 真实多人**；不得用服务端夹具替代图形与多人结论。

## 5. 委派失败协议（硬规则）
运行时确实没有真实子代理工具、真实派单失败且无替代、用户明确要求直接执行、或技术 / 授权限制阻止委派时，可不做委派。失败时必须：检查实际错误信息（不推测）；适当重试或换受支持的方法；**绝不用自我对话模拟代理，绝不编造派单记录**；说明观察到的限制；只有"为推进有用进展所必需"时才继续直接做并标注未委派。不得悄悄绕过，发生了要说出来。

## 6. 本项目附加硬约束（硬规则）
- 所有代码注释必须中文（标识符保持英文）。新建或修改文件时，顺带把遇到的英文注释改掉。
- 先找归属再写代码：按 `AGENTS.md` 的模块职责拆分，不把多职责塞进同一文件 / 同一方法。
- 正式存档与隔离测试分离：只替换目标模组；先备份；文件被锁时等玩家正常退出，**不得强杀游戏**。
- 大改动前提醒用户先落 git 提交点（用户硬性规则）。
- 提交范围：只含源码、文档、检查脚本与脱敏结果；不提交人物 / 世界、完整日志、反编译产物、凭据。
- 证据分级：隔离夹具 ≪ 图形客户端 ≪ 真实多人；不得用服务端夹具替代图形与多人结论（见第 4 节）。

## 7. 对外报告（硬规则）
对外报告要短、准、可验收：做了什么、改了哪些关键部分、验证是否真的通过、还有什么没解决。不倾倒中间发现，不搬运子代理完整过程记录。不掩盖失败，无证据不宣称成功。遇到限制（缺少工具、某类验证未做）必须写明。
