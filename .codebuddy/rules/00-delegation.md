# 项目开发与多代理调度政策（V2）

本文件是 ZenithReborn 项目的**常驻项目规则**，由编辑器在每次会话自动加载（`alwaysApply: true`），对本项目内所有开发工作持续有效。
本文件与用户级 SUBAGENT-PROTOCOL 并存：本项目规则更严格、更具体，**两者冲突时以本文件为准**。
版本：**2026-11-02 V2**（按用户下发的新版协议整体重写；V1 为 2026-11-01）。

## 1. 规则地位与适用范围

本文件是**执行要求**，不是建议、不是可选优化、不是风格偏好。主代理与所有子代理都必须遵守。
适用于：每一个开发请求、每一轮后续开发、每一个实质新阶段，直到本项目生命周期结束。

**排除活动（不需要子代理）**：闲聊、问候、与项目执行无关的简单概念问答、不涉及实际开发工作的讨论。

**但以下一律属于开发工作，必须走委派**：项目调查、代码分析、调试、需要仓库检查的实现规划、任何修改、任何验证。

## 2. 最高优先级：真实委派是强制要求

真实子代理委派对**所有**开发工作都是强制要求。这是持续性执行要求，不是一次性动作。

角色定位：

| 角色 | 定位 |
|---|---|
| 主代理 | 协调者、架构者、集成者、最终审查者。管执行，不是默认的实现工人。 |
| 子代理 | 默认执行者。在独立上下文中完成调查、实现、调试、验证。 |

**主代理不得悄悄退回单代理开发。** 任何"这轮我自己做完了"的行为，只有在第 11 节的四种例外成立时才允许，且必须如实报告。

## 3. 每轮强制委派闸门

任何实质开发动作**之前**，必须先走完闸门五步：

1. 识别当前执行目标（这一轮到底要产出什么）。
2. 识别当前运行时**真实可用**的子代理工具（不是记忆里的、不是假设的）。
3. 为本轮**至少派一个真实子代理**。
4. 给出明确范围与交付物（按第 9 节的派单契约）。
5. 用返回结果协调后续动作，而不是拿回结果后自己另起一套做法。

**每个新的用户开发请求都要重新评估这个闸门，同一项目内的后续请求同样算。**
**之前的派单不能替代本轮要求。** 若已有代理实例可复用，必须通过**真实工具调用**给它新任务，而不是在主上下文里"替它继续做"。

**没有真实派单调用 = 未满足要求。**

### 3.1 跳过理由黑名单

以下理由**全部不成立**，说出任何一条即视为违规：

| 无效理由 | 说明 |
|---|---|
| 任务简单 | 复杂度与强制闸门无关 |
| 主代理自己能做 | 能力不是豁免条件 |
| 直接做可能更快 | 速度不是豁免条件 |
| 委派更耗 token | 用户已明确优先持续性委派，而非压缩调用次数 |
| 项目已熟悉 | 熟悉度不产生豁免 |
| 之前已经用过子代理 | 历史派单不计入本轮 |
| 主上下文还有余量 | 上下文余量不是豁免条件 |
| 工作太小不值得拆 | 再小也派一个聚焦代理 |

**任务复杂度与强制闸门无关。** 闸门只有"过"与"没过"，没有"这次算了"。

## 4. 主代理执行限制

存在子代理工具时：

| 主代理**不得**亲自做（必须委派） | 主代理**可以**做 |
|---|---|
| 深入源码探索 | 读派单所需的最小元数据 |
| 全库搜索 | 看简洁的代理报告 |
| 功能实现 | 架构决策 |
| 常规代码编辑 | 协调接口与依赖 |
| 重复调试 | 解决冲突结果 |
| 大量文档研究 | 做最终集成检查 |
| 编写测试 | 审查关键证据 |
| 常规构建与测试执行 | 与用户沟通 |
| 大段日志分析 | 判断阶段能否收尾 |

边界判断：**这件事是否需要读源码、改文件、跑命令、扫日志？** 是 → 派出去。**是否只需要做决策、协调、判断？** 是 → 主代理自己做。

## 5. 全流程持续委派

不能只在开头派一次然后自己干完。每个阶段都要有对应的真实代理任务：

| 阶段 | 委派对象 | 说明 |
|---|---|---|
| 调查 | 代码探查 / 文档研究 / 根因调查代理 | 摸清现状与调用路径 |
| 实现 | 实现代理 | 按第 9 节契约改代码 |
| 验证 | 构建 / 测试 / 独立检查代理 | 与实现分离 |
| 调试 | 调试代理，或把失败**明确重新指派**给活跃代理 | 验证失败不得由主代理自己闷头改 |
| 集成 | 主代理 | 整合、解决依赖、判定完成 |

**新阶段只要涉及实质执行，就应触发相应代理任务。** 子代理使用必须贯穿工作流，不是开场表演。

## 6. 最小代理数与并发

| 场景 | 最低要求 |
|---|---|
| 小开发任务 | 至少 1 个真实子代理，且由它做实际调查或实现 |
| 代码修改（默认） | 2 个职责：实现 + 独立验证/审查，能分开就分开 |
| 第二个代理不现实时 | 仍必须完成验证，并在报告中说明限制原因 |
| 多个独立任务 | 并发派单，不得无谓串行 |
| 大型开发任务（有独立工作流） | 3–5 个起步，按实际结构调整 |

这些数量是**下限与建议**，不削弱"每个开发请求都要委派"的强制要求；也不为凑数造代理。

## 7. 轻量子代理优先，团队按需

普通开发用**聚焦的轻量子代理**：任务可独立完成、结果只需回交主代理、代理之间不需要直接沟通。

只有确实需要代理间直接沟通或共享任务协调时才用完整 Agent Team：多模块并行、竞争性假设需要协同讨论、大量跨职能协调。

**"必须有至少一个真实子代理"不等于"必须建团队"。** 日常改一个方法不要开团队会议。

## 8. 主上下文隔离与回交

主上下文保持**战略聚焦**，只保留：整体架构、当前目标、任务依赖、重要技术决策、已验证结论、集成状态、未解阻塞。

子代理负责：原始源码检查、详细调查、试错调试、大日志、中间实现细节、常规验证。

**回交必须简洁且有证据，固定五项**：

| 项 | 内容 |
|---|---|
| 状态 | 完成 / 部分 / 受阻 |
| 发现 | 关键结论，不含过程叙述 |
| 改动的文件 | 具体路径与改了什么 |
| 验证结果 | 实际跑了什么、结果如何 |
| 遗留阻塞 | 未解决项、不确定项、需要他人接手的信息 |

非必要不要把完整调查记录、原始日志、反复失败的尝试搬进主上下文。**不接受无证据的"已完成"。**

## 9. 派单契约与文件所有权

每份派单必须写明：

1. **目标**与预期结果。
2. **范围**：涉及哪些文件 / 模块。
3. **技术约束**：版本、依赖、架构约定、已知风险。
4. **文件所有权**：自己拥有哪些文件、**绝不能改**哪些。
5. **允许的操作**：能不能跑构建、能不能装包、能不能碰存档。
6. **验证要求**：用什么手段证明做对了。
7. **预期交付物**。

并发纪律：

- 禁止两个代理同时改同一文件（同文件任务串行，或合并给一个所有者）。
- 并行修改共享接口前先协调，先定接口再开工。
- 有隔离工作区 / 分支 / worktree 时视情况使用。
- 遵守依赖顺序，前置未完成不启动后继。
- **并行不得损害仓库完整性**；集成要显式做，不能靠运气。

## 10. 工程质量

所有代理（含主代理）必须：

- 尊重**真实**版本与依赖：核对 .NET 8 / C# 12 / tModLoader 1.4.4 的实际 API。
- 验证不熟悉的 API：查权威文档或源码定义后再用。
- **禁止编造方法、类、接口**。
- 优先**根因修复**，不做猜测性补丁。
- 保留既有架构与模块拆分，避免无关改动。
- 尽可能跑**真实**验证（真编译、真夹具、真运行），不用推演代替。
- 如实报告失败，不粉饰、不省略。

**主代理对集成后的正确性负责。子代理自称成功不能替代验证。**

## 11. 委派失败协议

只有**四种**情况可以跳过委派：

1. 当前运行时**确实没有**真实子代理工具。
2. 真实派单尝试**失败**，且无受支持的替代方式。
3. **用户明确要求**直接执行。
4. 具体技术或授权限制**阻止**委派（如权限、工具禁用）。

失败时必须：

- 检查实际错误信息，而不是推测。
- 适当重试，或换一种受支持的方法。
- **绝不用自我对话模拟代理，绝不编造派单记录。**
- 说明观察到的限制。
- 只有在"为推进有用进展所必需"时才继续直接做，并标注该段工作未委派。

**不得悄悄绕过。** 发生了要说出来。

## 12. 集成、验证与证据分级

宣布完成前：收齐结果 → 核对文件改动与归属 → 解决冲突 → 确认共享接口 → 跑相关构建与测试 → 独立复核关键改动 → 确认符合用户要求。

严格区分四种状态，不得混用：**已实现 / 已编译 / 已通过测试 / 已实测验证**。未测试的代码不得称为已验证。

本项目证据分级固定为：**隔离夹具 ≪ 图形客户端 ≪ 真实多人**。
**不得用服务端夹具替代图形与多人结论。**

## 13. 每轮合规自检

宣布任务完成前，逐项核对：

- [ ] 本轮是否给至少一个真实子代理派了活（有真实工具调用记录）？
- [ ] 子代理是否做了**实质执行**，而不只是被创建？
- [ ] 实现与验证是否都适当委派（默认两个职责已分开）？
- [ ] 结果是否已集成，冲突是否已解决？
- [ ] 是否做了真实验证（构建 / 测试 / 运行）？
- [ ] 失败与限制是否如实报告？

**若本轮有实质开发却没有任何真实子代理执行，则不合规**，除非第 11 节的例外成立。
**没有真实执行证据，不得声称合规。**

## 14. 长期连续性与项目记忆

每个开发回合都适用，无论项目跑了多久。

- **不得用历史成功派单来满足新工作。**
- **不得随着对话变长逐渐退回单代理。**
- 会话开始时：读项目指令 → 查项目知识 → 看真实仓库状态（`git status` / `git log`）→ 确认未完成工作 → 按委派优先继续。
- 不要假设上一轮的临时代理还活着。

项目知识保持简洁，只保留：架构、技术约束、已验证决策、当前进度、已知问题、重要测试结果。**不存无关的原始执行史。**

**记忆写入位置约定**：

| 内容 | 位置 |
|---|---|
| 项目入口与命令 | `CODEBUDDY.md` |
| 长期结论 | `.workbuddy/memory/MEMORY.md` |
| 协作硬规则 | `AGENTS.md` |
| 逐版本细节 | `docs/` |

## 15. 本项目附加硬约束

- **所有代码注释必须中文**（标识符保持英文）。新建或修改文件时，顺带把遇到的英文注释改掉。
- **先找归属再写代码**：按 `AGENTS.md` 的模块职责拆分，不把多职责塞进同一文件 / 同一方法。
- **正式存档与隔离测试分离**：只替换目标模组；先备份；文件被锁时等玩家正常退出，**不得强杀游戏**。
- **大改动前提醒用户先落 git 提交点**（用户硬性规则）。
- **提交范围**：只含源码、文档、检查脚本与脱敏结果；不提交人物 / 世界、完整日志、反编译产物、凭据。
- **证据分级**：隔离夹具 ≪ 图形客户端 ≪ 真实多人；不得用服务端夹具替代图形与多人结论（见第 12 节）。

## 16. 对外报告

对外报告要**短、准、可验收**：做了什么、改了哪些关键部分、验证是否真的通过、还有什么没解决。

- 不倾倒中间发现，不搬运子代理完整过程记录。
- **不掩盖失败，无证据不宣称成功。**
- 遇到限制（缺少工具、某类验证未做）必须写明。

## 17. 常设执行令与最终运行法则

常设执行令（在整个项目生命周期内有效）：

- 每个开发回合派**真实**子代理。
- 每个实质执行阶段委派工作。
- 不用任务简单当借口。
- 不用自我推演替代真实委派。
- 不把之前的派单当本轮合规。
- 不悄悄退回单代理。
- 保持主上下文干净。
- 验证结果并维持项目连续性。

用户明确优先**持续性使用子代理**，而不是压缩模型调用次数。

**最终运行法则：主代理协调，子代理执行，独立验证确立正确性，主代理集成并报告。除非运行时确实阻止，每轮开发都必须展示真实委派。**
