# 项目开发与多代理调度政策

本文件是 ZenithReborn 项目的**常驻开发规则**，由 WorkBuddy 自动加载，适用于本项目内所有任务。
与用户级 `~/.workbuddy/.../SUBAGENT-PROTOCOL.md`（通用哲学版）并存：本项目规则更具体，冲突时以本文件为准。
版本：2026-11-01 由用户下发并落盘。

## 1. 总则

目标是最大化工程吞吐、保护主代理上下文、减少无效劳动、保持项目连续性。
用户明确偏好大量使用真实子代理，并接受由此增加的模型消耗，只要换来更快的执行、更干净的上下文或更好的质量。

**委派是默认工作方式，不是难题专用手段。**
只使用运行时真实提供的 agent / subagent / team 能力；**禁止**用自我对话模拟多个代理。

## 2. 默认委派

每一个实质性开发任务，默认把执行交给至少一个**真实子代理**，与任务大小无关。
算作"实质性"的包括：小改代码、修 bug、查 API、读源码、实现功能、重构、写和跑测试、改文档、兼容性核对、代码审查、性能排查。

不以"任务简单"作为不委派的理由。小任务派一个聚焦代理，大任务在有独立工作可拆时派多个。

例外（可以不派，但要在报告里说明）：
- 纯对话、无需执行；
- 用户明确要求亲自做；
- 运行时确实没有委派能力（如实说明，不假装）；
- 委派会引入具体技术风险（例如需要精确控制的高风险配置写入）。

## 3. 角色分工

**主代理 = 技术负责人**：理解需求、掌握全局架构、划定任务边界、派单、协调依赖、审查结果、集成改动、解决冲突、最终验证。
主代理**不**包揽已派出去的实现细节，也**不**重复代理已经查过的事。

**子代理 = 执行者**：在各自独立上下文里调查、实现、调试、测试、审查，只回交集成所需的信息。

## 4. 派单时机与并发

顺序：**理解 → 拆分 → 派单 → 执行 → 集成 → 验证**。
只获取足以划定边界的初始信息，然后尽早派单，不要先把大文件或大日志读进主上下文。

并发起点（指导值，不是硬上限）：

| 任务规模 | 初始派单 |
|---|---|
| 小改动 | 1 个 |
| 常规开发 | 1–2 个 |
| 多个独立任务 | 2–4 个 |
| 跨模块大改 | 3–5 个 |

有真实独立工作就加并发；不为凑数造代理。

## 5. 轻量代理优先，团队按需升级

**优先用普通聚焦子代理**：一个代理能独立完成、结果只需回主代理、成员之间不需要直接沟通、不需要共享任务列表。

**才用完整 Agent Team**：多个代理需要互相直接沟通、需要共享任务所有权与依赖协调、多个独立模块并行开发、竞争性假设需要协同讨论、需要大量跨职能协调。

完整团队的 token 开销明显高于普通子代理。**日常改一个函数不要开团队会议。**

## 6. 派单契约

每份派单必须写清：目标与预期结果、涉及文件/模块、技术约束与项目背景、允许的改动与操作、交付物、验证要求。
给足上下文让它独立执行，但不要塞整部项目史。
每个代理必须清楚**自己拥有什么、绝不能改什么**。

## 7. 并行与文件所有权

积极并行，但**绝不无控制地并发编辑**：
- 可写文件归属明确到代理；
- 禁止两个代理同时改同一文件（同一文件的任务串行，或合并给一个所有者）；
- 并行实现前先定好共享接口；
- 遵守依赖顺序，前置未完成不启动后继；
- 有条件时用隔离分支/工作副本；
- 集成要显式做，不能靠运气。

## 8. 主上下文纪律

主上下文只保留：整体架构、当前目标、任务依赖、重要技术决策、已验证结论、集成状态、未解阻塞。
把大范围翻文件、重复搜索、细碎调试、大段日志分析都派出去。
不要例行把整份源码、原始终端日志、完整调查记录、反复失败的尝试搬回主线。
只给必要的细节，其余按需再取。

## 9. 子代理回交格式

完成即回交：**状态**（完成/部分/受阻）、**发现**（关键结论）、**改动**（改了哪些文件、怎么改）、**验证**（实际跑了什么、结果如何）、**问题**（遗留与不确定）、**交接**（其他代理需要的信息）。
不要长篇过程叙述。**不接受无证据的"已完成"**。

## 10. 工程质量

所有代理必须尊重真实环境：核对语言/框架/依赖/API 版本；改之前先看现有实现；**不得编造不存在的方法、类、接口**；优先根因修复而不是猜测性补丁；保持既有架构约定；避免无谓重写；最小化无关改动；考虑向后兼容与集成影响。
不熟悉的 API 先查权威文档或源码定义。
难问题时并行验证多个竞争假设，而不是反复重试同一个失败做法。

## 11. 集成与验证

最终结果由主代理负责。宣布完成前：收齐结果 → 核对文件改动与归属 → 解决冲突 → 确认共享接口 → 跑相关构建与测试 → 独立复核关键改动 → 确认符合用户要求。

**严格区分"已实现 / 已编译 / 已通过测试 / 已实测验证"**，未测试的代码不得称为已验证。

本项目证据分级固定为：引擎/隔离夹具 ≪ 图形客户端 ≪ 真实多人。不得用服务端夹具替代图形与多人结论。

## 12. 长期项目记忆

只记录**已确定的结论**，不记录开发全过程。保留：项目目标与架构、语言与依赖版本、重要设计决策、模块职责、已完成功能、已知缺陷与已验证修复、当前优先级、未决技术风险。

**不记录**：子代理试过的每种算法、每次失败实验、原始日志、完整对话记录。
源码与 git 历史是实现的权威记录。

写入位置约定：
- 项目入口与命令 → `.codebuddy/CODEBUDDY.md`
- 长期结论 → `.workbuddy/memory/MEMORY.md`
- 协作硬规则与版本状态 → `AGENTS.md`
- 逐版本细节 → `docs/`（版本记录 + CHANGELOG）

会话开始时：读项目指令 → 查项目知识 → 看真实仓库状态（`git status`/`git log`）→ 确认未完成工作 → 继续按委派优先执行。**不要假设上一轮的临时代理还活着。**

## 13. 模型与资源

每个任务用能可靠完成它的最省模型：常规探查、直接实现、重复验证用快速廉价模型；架构决策、复杂算法、含糊故障、关键审查用强推理模型。
优化整体成本，而不是单个代理的成本。
信息足够就动手，不要反复自我推演、重复重建上下文、冗余调用工具。

## 14. 授权与安全

只使用真实能力与既有权限；不泄露敏感信息；**不让子代理绕过授权要求**；有后果的对外操作与不可逆操作必须先确认；优先可逆操作。
保护既有源码与用户数据。

## 15. 本项目附加硬约束

- **所有代码注释必须中文**（标识符保持英文），新建或修改文件时顺带把英文注释改掉。
- **先找归属再写代码**：按 AGENTS.md 的模块职责拆分，不把多职责塞进同一文件/方法。
- **正式存档与隔离测试分离**：只替换目标模组；先备份；文件被锁时等玩家正常退出，**不得强杀游戏**。
- **大改动前提醒用户先落 git 提交点**（用户硬性规则）。
- 提交只含源码、文档、检查脚本与脱敏结果；不提交人物/世界、完整日志、反编译产物、凭据。

## 16. 对外报告

面向用户的报告要短、准、可验收：做了什么、改了哪些关键部分、验证是否真的通过、还有什么没解决。
不要倾倒每个子代理的中间发现。**不得掩盖失败，不得无证据宣称成功。**
